SECTION 1 — MASTER PROMPT  (paste this first, every time)
================================================================================

You are a senior product designer specialising in operational software for
institutional environments — the kind of tool a staff member uses several
hundred times a day and must never have to think about.

Design the complete user interface for the SMART LIBRARY MANAGEMENT SYSTEM
(SLMS), a web-based library automation system for the Central Library of World
University of Bangladesh. It replaces a manual, paper-register workflow that
suffers from slow record keeping, difficulty tracking borrowed books, fine
calculation errors, and no visibility into live availability.

THE SYSTEM SERVES FOUR ROLES:
  1. STUDENT       — searches the catalog, checks availability, views their own
                     loans, borrowing history, and outstanding fines.
  2. LIBRARIAN     — the power user. Works the circulation desk all day issuing
                     and returning books with a barcode scanner and a student ID
                     card scanner. Also manages the catalog, member records, and
                     operational reports.
  3. ADMINISTRATOR — manages user accounts and roles, configures system policy
                     (loan period, fine rate, borrowing limits), reviews the
                     audit log, and runs database backups.
  4. MANAGEMENT    — read-only. Views reports and dashboards for decision-making.

THE SINGLE MOST IMPORTANT DESIGN CONSTRAINT:
  The librarian's issue and return screens are SCANNER-FIRST. During a
  transaction the librarian's hands are on a physical book and a scanner gun —
  NOT on a mouse. A complete book issue must be achievable with two scans and
  one Enter key press. If your design requires the librarian to click a dropdown
  or hunt for a field mid-transaction, the design has failed.

DESIGN PHILOSOPHY — apply all six:
  1. CLARITY OVER DECORATION. This is a working tool used under queue pressure.
     Every pixel earns its place. No ornament, no gradients-for-the-sake-of-it,
     no decorative illustration on operational screens.
  2. SPEED OF COMPREHENSION. A librarian glancing at a screen for one second
     must know: who is this student, is the book available, is there a fine.
     Use size, weight, and colour to establish that hierarchy.
  3. ERROR PREVENTION OVER ERROR MESSAGES. Disable what cannot be done. Show
     eligibility before the action, not after. Confirm destructive actions.
  4. CONSISTENCY IS NON-NEGOTIABLE. One status colour system, one button
     hierarchy, one table pattern, one form pattern — used identically on every
     screen in the system.
  5. ACCESSIBLE BY DEFAULT. WCAG 2.1 AA contrast, visible focus rings, full
     keyboard operability, minimum 44x44px touch targets, never colour alone as
     a meaning carrier (always pair colour with an icon or text label).
  6. GRACEFUL ON OLD HARDWARE. The library runs Core i3/i5 machines with 8 GB
     RAM at 1366x768. Design for fast rendering: no heavy imagery, no complex
     animation, no infinite-scroll virtualisation.

TONE OF VOICE:
  Professional, calm, plain-language. Never jargon. Never cute.
  Good:  "This student has reached the 3-book borrowing limit."
  Bad:   "Oops! Something went wrong :("
  Good:  "Book returned 4 days late. Fine: ৳20.00"
  Bad:   "ERR_OVERDUE_FINE_CALC_TRIGGERED"

3.1 BUTTONS

           loading (spinner replaces the icon, label stays, button disabled)

RULE: exactly ONE primary button per screen region. The primary action on a
      circulation screen is always the large one, always bottom-right of the
      action bar.

3.2 FORM INPUTS
--------------------------------------------------------------------------------
Text input   40px height, 1px Border, 6px radius, 12px horizontal padding,
             14px text, placeholder in Text muted
Label        12px/500 Text secondary, 6px above the field, always present —
             never rely on a placeholder as the label
Helper text  12px Text muted, 4px below
Error state  1px Red 600 border, Red 50 background tint, 12px Red 700 message
             below with an alert icon
Required     red asterisk after the label
Disabled     Grey 100 background, Text muted, not-allowed cursor
Select       same metrics as text input, chevron-down 16px at right
Date input   native date picker, DD Mon YYYY display format
Search input  magnifier icon left inset, clear (x) button right when filled

3.3 SCANNER INPUT  ★ THE SIGNATURE COMPONENT
--------------------------------------------------------------------------------
This is the most important component in the entire system. Design it with care.

Physical behaviour: the scanners are keyboard-wedge devices. They type the
barcode characters rapidly then send Enter. The field must auto-focus on page
load, auto-submit on Enter, then re-focus itself for the next scan.

Dimensions: full width of its card, 72px tall, 8px radius, 2px border.
Content:    scan-line icon 32px on the left, then the value in 20px monospace.

FOUR STATES — design each explicitly:

  [IDLE / WAITING]
    2px dashed Primary 500 border, Primary 50 background.
    A slow pulsing animation on the border (2s cycle) signalling "ready".
    Text: "Scan student ID card…"  (or "Scan book barcode…")
    Below, in 12px Text muted: "or type the number and press Enter"
    A blinking text cursor is visible.

  [SCANNING / PROCESSING]
    Solid 2px Primary 600 border, white background.
    The scanned value renders live in 20px monospace as it arrives.
    A small spinner appears at the right edge.
    Text below: "Verifying…"

  [SUCCESS]
    Solid 2px Green 600 border, Green 50 background.
    Check-circle icon 32px in Green 600 replaces the scan icon.
    The scanned value in 20px monospace, Green 700.
    The resolved record (student or book) expands into a detail panel below.
    Optional: a short success chime, user-toggleable.

  [ERROR]
    Solid 2px Red 600 border, Red 50 background, x-circle icon in Red 600.
    The scanned value shown so the librarian can see what was actually read.
    A plain-language reason directly below in Red 700, e.g.
      "Card not recognised. Register this card in Student Management."
      "This copy is already issued to student 3927 (due 12 Aug 2026)."
    A "Scan again" affordance; the field auto-clears and re-focuses after 3s.

3.6 CARD
--------------------------------------------------------------------------------
White surface, 1px Border, 8px radius, 24px padding, Level 1 elevation.
Optional header row: H3 title on the left, action(s) on the right, 1px divider

3.7 STAT TILE (dashboard KPI)
--------------------------------------------------------------------------------
Card containing: 12px uppercase Text secondary label; 32px/700 value; an
optional 12px delta line with an up/down arrow in green or red; a 20px icon in
the top-right tinted with the relevant semantic colour. The entire tile is
clickable and navigates to the filtered list it summarises.

3.8 ALERT / BANNER
--------------------------------------------------------------------------------
Full width of its container, 12px radius, 16px padding, 4px left accent bar in
the semantic colour, 20px icon, 14px/600 title, 14px/400 body, optional close
button. Four variants: success, warning, danger, info.

3.9 MODAL
--------------------------------------------------------------------------------
Centred, max-width 480px (560px for forms), 12px radius, Level 3 elevation,
backdrop rgba(15,23,42,0.5). Header with title and close (x). Footer action bar
right-aligned: Cancel (ghost) then the primary or danger action. Traps focus,
closes on Escape, returns focus to the trigger on close.

Destructive confirmations must restate the specific consequence:
    "Delete 'Database System Concepts'? This title has 3 copies and 47
     historical loan records. This cannot be undone."

3.10 NAVIGATION SHELL
--------------------------------------------------------------------------------
Sidebar     240px wide, white surface, 1px right border, collapsible to 64px
            (icons only). Logo block at top (64px tall). Nav items 40px tall
            with a 20px icon + 14px label; active item has Primary 50
            background, Primary 700 text, and a 3px Primary 600 left bar.
            Items are grouped with 11px uppercase section labels.
Topbar      64px tall, white, 1px bottom border. Left: sidebar toggle + current
            page title. Right: global search (librarian/admin only),
            notification bell with count badge, user menu (avatar + name + role
            chip, dropdown with Profile / Change password / Log out).
Mobile      sidebar becomes an off-canvas drawer behind a hamburger; the topbar
            stays fixed.

3.11 PRINT LAYOUT
--------------------------------------------------------------------------------
Hide all navigation and interactive chrome. Black on white, no background
fills. Header carries the university name, "Central Library", the document
title, and the generation timestamp. Footer carries page N of M. Tables use
visible 1px rules. Receipts are sized for 80mm thermal paper; reports are A4
portrait (landscape where a report exceeds 6 columns).

SECTION 5 — INTERACTION & MOTION
================================================================================

Motion budget: 150ms for micro-interactions (hover, focus), 200ms for
transitions (dropdown, tab), 250ms for modal enter/exit. Easing: ease-out for
entering, ease-in for exiting. Respect prefers-reduced-motion by disabling all
non-essential animation.

Feedback rules:
    - Every action produces visible feedback within 100ms.
    - Operations over 400ms show a loading state on the triggering control.
    - Success feedback appears as a toast (top-right, auto-dismiss 4s) for
      non-blocking actions, and inline for form submissions.
    - Errors NEVER auto-dismiss.
    - Toasts stack vertically, maximum 3 visible.

Keyboard model (must be fully specified in the design):
    Tab / Shift+Tab   move focus in visual order
    Enter             submit the focused form or activate the focused control
    Escape            close modal / clear the scanner field
    /                 focus the global search
    Alt+I             go to Issue Book       (librarian)
    Alt+R             go to Return Book      (librarian)
    Alt+S             go to Search           (all)
    Arrow keys        navigate table rows and dropdown options

Focus ring: 2px Primary 600, 2px offset, on every interactive element. Never
remove it. Never replace it with only a colour change.

SECTION 6 — CONTENT & MICROCOPY RULES
================================================================================

Dates       "13 Aug 2026"           never 13/08/26 (ambiguous)
Date+time   "13 Aug 2026, 2:45 PM"
Relative    "Due in 3 days" / "4 days overdue"  — pair with the absolute date
Currency    "৳20.00"                always 2 decimals, symbol before
Numbers     "1,248"                 thousands separators
IDs         monospace: 4018, ACC-00231, 978-0-07-352332-3
Names       Title Case as entered; never uppercase a person's name

Button labels are verbs describing the outcome:
    "Issue Book"  not  "Submit"
    "Confirm Return"  not  "OK"
    "Collect Fine"  not  "Save"

Error messages state (a) what happened, (b) why, (c) what to do next:
    "Cannot issue this book. Sowmika Islam Suchi already has 3 books on loan,
     which is the limit. Return a book first, or ask an administrator to raise
     the limit."

Empty states state what the area is for and offer the next action:
    "No books issued today. Issued books will appear here as you process them.
     [Issue a Book]"

Confirmations name the specific object and the specific consequence.
Never use "Are you sure?" alone.

SECTION 7 — ACCESSIBILITY REQUIREMENTS (WCAG 2.1 AA)
================================================================================

  [ ] All text meets 4.5:1 contrast; large text and UI components meet 3:1
  [ ] Colour is never the sole carrier of meaning — always paired with an icon
      or a text label (critical for the status badge system)
  [ ] Every interactive element is reachable and operable by keyboard alone
  [ ] A COMPLETE BOOK ISSUE AND RETURN CAN BE PERFORMED WITHOUT A MOUSE
  [ ] Visible focus indicator on every focusable element
  [ ] Logical heading hierarchy (one H1 per page, no skipped levels)
  [ ] Every form input has a programmatically associated label
  [ ] Errors are announced to screen readers (aria-live="assertive")
  [ ] Status changes are announced politely (aria-live="polite")
  [ ] Tables use proper th/scope markup with captions
  [ ] Modals trap focus and restore it on close
  [ ] Touch targets are at least 44x44px
  [ ] "Skip to main content" link as the first focusable element
  [ ] Page title updates on navigation
  [ ] prefers-reduced-motion honoured

S-08 · ISSUE BOOK  ★ DESIGN THIS FIRST
--------------------------------------------------------------------------------
Design the Issue Book screen — the librarian's most-used screen, operated
several hundred times a day with a scanner in hand.

Layout: standard app shell (240px sidebar, 64px topbar). Content is a single
centred column, max-width 720px, so nothing competes for attention.

Structure, top to bottom:

  1. Page header: H1 "Issue Book", and on the right a small muted line showing
     today's date and the librarian's name.

  2. STEP 1 CARD — "Scan Student ID Card"
     Contains the scanner-input component (§3.3) in its idle state.
     ON SUCCESS the card expands to show the student panel:
        - Student number in monospace, and full name in H2
        - Department and batch in Text secondary
        - Three inline stat chips: "Active loans 1 of 3" |
          "Outstanding fine ৳0.00" | "Member since Jan 2024"
        - A prominent eligibility badge: ELIGIBLE (green) or BLOCKED (red)
        - If blocked, a red alert banner naming the exact reason and the
          remedy — and Step 2 stays disabled and visibly dimmed.
        - A small "Change student" ghost link to re-scan.

  3. STEP 2 CARD — "Scan Book Barcode"
     Disabled and dimmed until Step 1 succeeds. Then the scanner-input
     activates and auto-focuses.
     ON SUCCESS the card expands to show the book panel:
        - Accession number in monospace, and the title in H2
        - Author, category, and shelf number in Text secondary
        - Availability badge: AVAILABLE (green) or ISSUED (amber)
        - If already issued, a red alert stating who holds it and its due date,
          and the confirm action stays disabled.
        - A book cover thumbnail (64x88px) on the left if one exists;
          otherwise a neutral book-icon placeholder.

  4. SUMMARY CARD — appears only when both steps succeed.
     A clean two-column key/value block:
        Issue date   30 Jul 2026
        Due date     13 Aug 2026   ← rendered larger and in Primary 700
        Loan period  14 days
     Below it, a muted line: "The student will owe ৳5.00 per day after the due
     date."

  5. ACTION BAR — sticky at the bottom of the column.
     Left: "Cancel" (ghost). Right: "✓ Confirm Issue" (primary, LARGE 48px).
     The confirm button is disabled until both scans succeed.
     Show the keyboard hint "press Enter" beside it.

Also design these states of this screen:
   (a) Fresh/empty — only Step 1 active, Step 2 dimmed
   (b) Student verified, book not yet scanned
   (c) Both verified, ready to confirm
   (d) Student blocked by outstanding fine (red path)
   (e) Book already issued to someone else (red path)
   (f) Card not recognised (red path)
   (g) Submitting (button in loading state)
   (h) Success — full-card green confirmation with a "Print receipt" primary
       action and a "Issue another book" secondary action

S-09 · RETURN BOOK  ★ DESIGN THIS SECOND
--------------------------------------------------------------------------------
Design the Return Book screen. Single-step and faster than issuing: the
librarian scans only the book barcode; the system finds the loan record.

Layout matches S-08 (centred 720px column) for muscle-memory consistency.

  1. Page header: H1 "Return Book".

  2. SCAN CARD — "Scan Returned Book"
     The scanner-input component, auto-focused, idle state.

  3. LOAN RECORD PANEL — appears on a successful scan:
        - Book: accession number (monospace), title (H2), author
        - Borrower: student number, name, department
        - A date row of three items, evenly spaced:
             Issued 16 Jul 2026 | Due 30 Jul 2026 | Returning 03 Aug 2026
        - A large, unmissable outcome block:

          ON TIME →  green panel, check-circle icon,
                     "Returned on time. No fine."

          OVERDUE →  red panel, alert-triangle icon,
                     "4 days overdue"  in H1-size
                     "Fine: ৳20.00"    in Display size, Red 700
                     a breakdown line: "4 days × ৳5.00 per day"
                     and a checkbox: "Collect fine now" (checked by default)

  4. ACTION BAR — "Cancel" (ghost) and "✓ Confirm Return" (primary, 48px).

States to design:
   (a) Waiting for scan
   (b) On-time return (green outcome)
   (c) Overdue return with fine (red outcome)
   (d) Barcode not found / not currently on loan (error)
   (e) Success confirmation, offering "Return another book"

S-03 · BOOK SEARCH & RESULTS
--------------------------------------------------------------------------------
Design the catalog search screen, used by both students and librarians.

  1. A prominent search hero at the top: a 56px-tall search input with a
     magnifier icon, placeholder "Search by title, author, ISBN, or keyword…",
     and a primary "Search" button. Below it, four quick-filter chips:
     All | Available Now | Newly Added | Most Borrowed.

  2. A results toolbar: "348 results for 'database'" on the left; on the right
     a sort select (Relevance / Title A–Z / Newest / Most borrowed) and a
     grid/list view toggle.

  3. A left filter sidebar (280px, collapsible):
        Category      checkbox list with counts
        Availability  radio: All / Available only
        Author        searchable checkbox list
        Year          range slider
        Language      checkbox list
     With an "Apply filters" primary button and a "Clear all" ghost link.

SECTION 11 — REVIEW CRITERIA (the design is done when all pass)
================================================================================

  1. A librarian can complete a book issue using ONLY a scanner and the Enter
     key — no mouse, no more than two scans.
  2. Every status in the system is communicated by BOTH colour and a label.
  3. Nothing in the interface uses a colour, spacing value, or type size that
     is not in the design system.
  4. Every error message says what happened, why, and what to do next.
  5. Every screen has a designed empty state and a designed error state.
  6. Every screen is usable at 1366x768 without horizontal scrolling.
  7. All text passes WCAG AA contrast.
  8. A first-time student user can find a book and check its availability
     without instruction.
  9. No screen requires more than 3 clicks from the dashboard.
 10. The design would still be legible and usable printed in greyscale.
